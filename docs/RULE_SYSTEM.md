## 1. 규칙 모델

두 종류이고 **섞지 않는다**(기획서 §10 "이 두 기능을 명확하게 구분한다").

| | 실행 전 확인 (`intercept`) | 실행 확인 (`check`) |
|---|---|---|
| 목적 | 충동 억제 | 할 일 상기 |
| 대상 앱 | **여러 개** | **하나**(기획서 §14 "권장"을 MVP 규칙으로 올린다 · 결정 #3) |
| 요일 | 월~일 중 고른 요일 | 월~일 중 고른 요일 |
| 시간 | 시작 ~ 끝(시간대 · 자정을 넘을 수 있다 · 기획서 §6 `20:00~02:00`) | 확인 시각 하나 |
| 메시지 | 규칙당 1개(MVP) | 규칙당 1개(MVP) |
| 개입 | 확인 화면 `[취소] [열기]` | 알림 `[나중에] [<앱> 열기]` |
| ON/OFF | 있음 | 있음 |

공통 필드(저장 형태 출발안 · Phase 1 에서 `docs/DATABASE.md` 로 확정한다):

```
rule
  id            UUID
  kind          'intercept' | 'check'
  name          사용자가 붙인 이름 (예: 업무시간)
  enabled       ON/OFF
  days          요일 7비트 (월=bit0 … 일=bit6 · 한 주는 월요일에 시작한다고 보고 화면도 월부터 그린다 · 기획서 §13 그림)
  message       사용자 메시지 (빈 값 불가)
  start_min     intercept: 시작 분(0~1439) · check: 확인 시각 분
  end_min       intercept: 끝 분 · check: 없음
  created_at · updated_at
rule_app
  rule_id · package_name · (표시용) app_label_snapshot
```

- 🔴 **메시지는 사용자가 쓴 글 그대로 보여 준다.** 다듬거나 바꾸지 않는다(기둥 4 · 기획서 §29 "사용자가 직접 만든 메시지 표시").
  기획서 예시 *"100kg이 넘는데 배달을 시킨다고?"* 처럼 거칠어도 사용자의 말이다.
- 앱 표시 이름은 저장 당시 이름을 같이 남긴다. 앱이 지워져도 규칙 목록이 깨지지 않게 한다(§7 엣지).
- ✅ 결정 #27: 이 앱 · 홈 런처 · 시스템 설정 · 전화는 자동 제외. ~~⚠ 미결정 L: 대상으로 고를 수 없는 앱(이 앱 자신 · 홈 런처 · 시스템 설정 · 전화)을 정한다. **추천: 자동 제외.**
  설정 앱이 대상이면 권한을 끄러 가는 길에 확인 화면이 뜬다. 전화가 대상이면 긴급 통화 앞에 화면이 끼어든다.~~

### 1.1 입력 검증

- 요일은 최소 하나.
- intercept 의 시작과 끝이 같으면 저장하지 않는다. ~~(종일 규칙은 MVP 에 없다 · 기획서에 없다)~~ → **하루 종일은 00:00 ~ 23:59 로 저장하고 끝 23:59 를 24:00 으로 판정한다**(결정 #38 · 2026-10-09).
- 메시지 길이 상한은 확인 화면 레이아웃으로 정한다(placeholder 2026-10-06 · 80자).

## 2. 하루 · 요일 · 시간대

- 기획서 §15: *"실행 여부는 날짜 단위로 관리한다. 날짜가 변경되면 새로운 하루로 판단한다."*
- ✅ **결정 #26**: 하루는 **기기 시간 자정**에 바뀐다. ~~⚠ 미결정 B: 하루가 바뀌는 시각.~~ 기획서 그대로면 **기기 시간 자정**이다. 형제 `mission` 은 새벽 4시를 쓴다(결정 #5).
  추천: **자정**. 이 앱의 "오늘"은 확인 시각(예: 23:00)까지의 하루라서 4시 경계의 이득(자정 넘어 한 일을 그날로 친다)이 작다.
- 날짜 키는 `YYYY-MM-DD`(기기 로컬). 기록마다 **날짜 키 + 실제 시각(UTC) + 그때의 시간대**를 함께 저장한다(mission `CLAUDE.md` §5-1 승계).
  날짜 계산은 순수 모듈 하나(`lib/day.ts` 예정)만 한다. 화면 · 네이티브 · DB 가 각자 날짜를 계산하지 않는다.
- ✅ **결정 #26**: 자정을 넘는 시간대는 **시작한 날의 요일**로 본다. ~~⚠ 미결정 C: 자정을 넘는 시간대의 요일.~~ 예: "야식 방지 · 금요일만 · 20:00~02:00" 일 때 **토요일 01:00** 은 걸리는가?
  추천: **시작한 날의 요일로 본다**(금요일 밤의 연장이다). 반대로 하면 "월~금 · 22:00~02:00" 규칙이 토요일 새벽엔 안 걸리고 월요일 새벽엔 걸린다.

## 3. 실행 전 확인 (`intercept`)

### 3.1 판정

대상 앱이 **화면 앞으로 나왔을 때**(감지 방법은 `ANDROID_PLATFORM.md` §2) 아래를 모두 만족하면 확인 화면을 띄운다.

```
규칙.enabled
∧ 패키지 ∈ 규칙.대상 앱
∧ 지금이 규칙 시간대 안 (§2 의 요일 판정 포함)
∧ 이 패키지에 통과 상태가 없다 (§3.3)
```

- 판정은 **순수 함수**로 둔다: `(규칙 목록, 패키지, 지금 시각, 시간대, 통과 상태) → 띄울 규칙 | 없음`. 네이티브 쪽은 이 결과만 받는다.
  가드로 요일 × 시각 × 자정 넘김 × 통과 상태를 전수로 잰다.
- ✅ **결정 #26**: 한 번만 묻고 메시지는 **무작위로 하나**. 판정 함수는 무작위 값(seed)을 인자로 받아 결정적으로 남는다(TS ⇄ Kotlin 같은 시험표). ~~⚠ 미결정 F: 같은 앱이 동시에 활성인 규칙 둘 이상에 걸리면(예: 업무시간 + 야식 방지가 겹치는 시간) 무슨 메시지를 띄우나.~~
  ~~추천: **한 번만 띄운다. 메시지는 가장 최근에 수정한 규칙의 것.** 연달아 두 번 묻는 것은 기둥 1(한 번만)에 어긋난다.~~ → 사용자는 "무작위로 하나"를 골랐다(2026-10-08).

### 3.2 확인 화면

```
<사용자 메시지>
<둘째 줄: 규칙 이름으로 자동 생성 · ~~예 "지금은 <규칙 이름> 시간이에요"~~ → "‘<규칙 이름>’ 규칙이 켜져 있어요" / en "“<rule name>” is on" (2026-10-09 · 이름이 "업무시간"이면 "시간 시간"이 되고 받침에 따라 이에요 / 예요가 갈린다 · 시안 세션 지적 · 🔴 ChatGPT 문구 검수 전)>

[취소]        [열기]
```

- 둘째 줄은 **규칙 이름으로 자동 생성**한다(결정 #27). 기획서 §5 그림의 *"지금은 업무시간이야."* 자리다. 문구는 검수 대상(`KOREAN_WRITING.md` §2).

- **[취소]**: 대상 앱을 쓰지 않는다. **홈 화면**으로 보낸다(결정 #27). ~~⚠ 미결정 E: 어디로 보내나.~~ 추천: **홈 화면**. 직전 앱으로 돌려보내면 직전 앱이 대상 앱일 때 다시 걸린다.
- **[열기]**: 대상 앱을 그대로 쓴다. 통과 상태를 만든다(§3.3).
- 뒤로가기 버튼은 **[취소]와 같다**(기둥 3 · 막는 앱이 아니므로 화면을 피할 길을 하나 더 둔다).
- 🚫 확인 화면에 타이머 · 강제 대기 · 문제 풀기 · 연속 탭 같은 **문턱을 두지 않는다**(기획서 §29 · 결정 #1). 한 번 묻고 끝이다.

### 3.3 통과 상태 (기획서 §17)

[열기]를 누른 직후 같은 앱을 다시 감지해 확인 화면이 되풀이되면 안 된다.

- 기획서 원문: *"일정 시간 동안 재감지 무시"* + *"사용자가 직접 YouTube를 종료하고 나중에 다시 실행하면 새로운 Confirm을 표시한다."*
  두 문장이 서로 다른 기준을 말한다(시간 기준 · 앱 이탈 기준).
- ✅ **결정 #27 · #28**: 앱에서 벗어나고 **기본 1분**이 지나면 끝난다. 사용자가 **1 / 3 / 5 / 10 / 15 / 30분** 중에서 바꾼다(0초 없음). **규칙마다** 고른다(결정 #29). ~~⚠ 미결정 D: 통과가 언제 끝나나.~~ 추천: **그 앱이 화면에서 벗어난 뒤 유예 시간이 지나면 끝난다**(유예 placeholder 2026-10-06 · 60초).
  - 유예가 없으면: 유튜브에서 알림창을 내리거나 공유 시트를 열었다가 돌아오는 것만으로 다시 묻는다.
  - 고정 시간(예: 10분)만 쓰면: 10분 넘게 보고 있던 앱 안에서 화면이 바뀔 때 다시 물을 수 있다(감지 방식에 따라 다르다 · `ANDROID_PLATFORM.md` §2).
- 통과 상태는 **패키지 단위**다. 유튜브를 통과시켜도 인스타그램은 따로 묻는다(기획서 §31 10:42 · 14:10 장면).
- **벗어남이 아닌 것**(결정 #19 · 2026-10-08): 잠금 화면 · 알림창(systemui) · 키보드 · 통화 · 알람 · 타이머 · 이 앱 자신. 통화가 길어도 돌아오면 이어서 쓴다.
- **고르지 않고 닫힌 확인 화면**(홈 · 잠금 · 다른 앱이 덮음)은 "대기 중"으로 남는다. 그 앱이 다시 보이면 같은 패키지여도 다시 묻는다(gap-hunt L1 · 홈 제스처 구멍 2026-10-08).
- [열기]는 확인 화면을 걷을 뿐 아니라 그 앱을 직접 실행한다(그사이 꺼졌어도 앱이 나온다 · L3).
- PIP · 분할 화면은 "맨 앞 앱 하나"만 본다(결정 #19).
- 통과 상태는 메모리에만 둔다(재부팅 · 프로세스 종료 시 사라져도 된다. 다시 한 번 묻는 것이 손해가 작다).

## 4. 실행 확인 (`check`)

### 4.1 판정

규칙의 확인 시각이 되면:

```
규칙.enabled ∧ 오늘 요일 ∈ 규칙.days
  ∧ 오늘(§2) 0시부터 지금까지 대상 앱 실행 기록이 없다
  ∧ 오늘 이 규칙으로 알림을 보낸 적이 없다
→ 알림
```

- 기획서 §7: **앱 안에서 무엇을 했는지는 보지 않는다.** "오늘 이 앱을 열었는가?"만 본다. 몇 분 썼는지도 안 본다(기획서 §15).
- 기획서 §16: **하루 최대 1회.** [나중에]를 눌러도 다시 알리지 않는다. 다시 알림은 이후 기능이다(기획서 §26 Pro 후보).
- ✅ **결정 #26**: 화면 앞에 나오면 실행이다. 우리 알림으로 연 것도 친다. ~~⚠ 미결정 K: "실행"의 정의.~~ 아래를 실행으로 칠지:
  - 우리 알림의 [<앱> 열기]로 연 것 → 추천: **친다**(그래야 "알림 후 실행"을 셀 수 있다 · 기획서 §18).
  - 다른 앱이 잠깐 띄운 화면(공유 · 로그인 창 등) → 추천: **화면 앞에 나왔으면 친다**(단순한 기준 · 기획서 §7).
- ✅ **결정 #28**: 확인 시각을 놓치면(알람 창 확인 시각 + 10분이 끝난 뒤에 깨면) **버린다.** ~~⚠ 미결정 J: 확인 시각을 놓쳤을 때(기기 꺼짐 · 절전으로 알람이 늦음). 추천: **그날 안이면 늦게라도 한 번 보낸다. 날이 바뀌었으면 버린다.**~~ → 사용자는 "정해진 시각을 놓치면 버림"을 골랐다.
  ⚠ 정확한 시각에 울리는 알람은 Play 정책 · Android 권한이 걸린다(`ANDROID_PLATFORM.md` §4).

### 4.2 알림

```
📔 <앱 이름>
<사용자 메시지>
[나중에]   [<앱 이름> 열기]
```

- [<앱> 열기]: 대상 앱을 실행한다(설치돼 있지 않으면 알림을 띄우지 않고 규칙에 경고 표시 · §7).
- [나중에]: 알림을 닫는다. 기록에 "알림 후 미실행 후보"로 남긴다.
- 🔴 알림 문구에 비난 · 실패 표현을 덧붙이지 않는다(기획서 §29 "목표 실패 처벌" 안 한다). 사용자 메시지만 보인다.

## 5. 기록 (첫 빌드부터 저장)

> 🔴 만 14세 미만으로 답한 기기(결정 #41)는 기록을 기기에만 둔다(기기 통계 집계). 서버로 올리지 않고 대기열을 비운다.

기획서 §20 이 저장 대상으로 "앱 실행 여부" · "Confirm 결과"를 적었다. 통계 화면(§6)을 넣든 안 넣든 **기록은 첫 빌드부터 쌓는다.**
나중에 통계를 붙일 때 지난 기록이 없으면 보여 줄 것이 없다(mission `CLAUDE.md` §7 의 같은 논리).

```
intercept_event   id · rule_id · package · date_key · at_utc · tz · result('cancel' | 'open' | 'dismissed')
launch_day        package · date_key · first_at_utc · via('self' | 'our_notification')   ← 패키지 × 날짜 1행
check_event       id · rule_id · date_key · result('already' | 'notified' | 'opened_after' | 'not_opened')
```

- ⚠ `launch_day` 는 **규칙의 대상 앱만** 적는다. 사용자의 모든 앱 사용 기록을 모으지 않는다(기둥 6 · 기획서 §21 "앱이 실행되었는지만 확인").
- ~~🔴 기록은 기기 밖으로 나가지 않는다(기획서 §20 · 기둥 6).~~ → 기록의 **사본이 서버로 간다**(결정 #22 · 2026-10-08). 기기가 정본이다. 하루 1회 요약에 대상 앱 이름별 통계가 실린다(결정 #21). 메시지 원문은 싣지 않는다.
- 기록은 지우지 않는다. 규칙을 지우면 규칙은 tombstone 으로 남기고 기록의 `rule_id` 가 살아 있게 한다(통계가 깨지지 않게).

## 6. 통계 (기획서 §18 · §19)

- 기획서: *"통계는 보조 기능이다. 앱의 주인공으로 만들지 않는다."*
- ✅ **결정 #28**: **MVP 에 통계 화면을 넣는다.** ~~⚠ 미결정 G: MVP 에 넣는가.~~ 기획서 §23 MVP 목록 17개에는 **통계가 없다.** §18 · §19 는 화면 예시까지 있다.
  추천: **MVP 는 홈의 규칙 카드에 "이번 주 N회 · 오늘 ✓" 한 줄만**, 통계 화면은 MVP 이후. 기록(§5)은 어느 쪽이든 쌓는다.
- 🔴 어느 쪽이든 ✓ 의 뜻을 화면에 밝힌다: **"앱을 열었다"이지 "일기를 썼다"가 아니다**(기획서 §19).
- 셀 것(기획서 §18 출발안): intercept = 확인 · 취소 · 그대로 열기. check = 목표일 · 미리 실행 · 알림 후 실행 · 미실행.
  파생값은 저장하지 않고 §5 기록에서 계산한다.

## 7. 엣지 (gap-hunt 전 출발 목록 · `docs/EDGE_CASES.md` 가 생기면 옮긴다)

| 상황 | 기대 동작 | 출처 |
|---|---|---|
| 감지 권한이 꺼졌다(사용자 · OS · 업데이트) | 홈에 경고 · 해당 규칙 카드에 "지금 동작하지 않아요" · 켜는 길 안내. 조용히 안 되는 것이 최악이다 | 기둥 5 |
| 대상 앱이 지워졌다 | 규칙은 남기고 그 앱 줄에 "설치돼 있지 않음" 표시 | §1 |
| 대상 앱이 업데이트 · 재설치됐다 | 패키지 이름이 같으면 그대로 동작 | — |
| 확인 화면이 떠 있는 동안 전화가 온다 | 전화가 이긴다. 확인 화면은 [취소]와 같이 처리하지 않고 그냥 닫혔다(`dismissed`)로 기록 | §5 |
| 시간대가 바뀌었다(여행) | 기기 현재 시간대의 벽시계로 판정한다(09:00~18:00 은 현지 09:00~18:00) | §2 |

| check 규칙 대상 앱을 intercept 로도 걸었다 | 둘 다 그대로 동작한다. intercept 에서 [열기]로 들어간 것도 그날의 실행이다 | 미결정 K |
