## 1. 이 앱에서 "오류"는 대부분 크래시가 아니다

오늘 갤럭시 S24 에서 실제로 난 것은 전부 **조용한 실패**였다. 앱은 안 죽었고 아무 예외도 사용자에게 안 보였다.

| 종류 | 오늘 실례 | Play vitals 에 잡히나 |
|---|---|---|
| 크래시 · ANR | 없음 | ✅ |
| 확인 화면이 저절로 닫힘 · 다시 안 뜸 | 16:21 · 16:39 | ❌ |
| 설정 화면 직행 거부 | `SecurityException`(16:08) | ❌(우리가 잡아서 넘겼다) |
| 서비스가 제조사 절전에 죽음 | 아직 없음(삼성에서 흔하다 △) | ❌ |
| 백그라운드 실행이 막혀 확인 화면이 안 뜸 | 이 폰에서는 없음(대체 오버레이를 안 탔다) | ❌ |

→ **크래시 도구만으로는 이 앱의 실패를 거의 못 본다.** 우리가 직접 "실패 신호"를 정의해 모아야 한다.

## 2. 실패 신호 목록 (기기마다 다를 수 있는 것)

| 신호 | 어떻게 안다 | 기능 |
|---|---|---|
| `crash` · `anr` | Play Console vitals(자동) · 다음 실행 때 `ApplicationExitInfo`(API 30+) | 공통 |
| `killed_by_system` | `ApplicationExitInfo` 의 종료 이유(메모리 · 제조사 절전 등) ✔ API · △ 제조사별 값 | 공통 |
| `service_lost` | 규칙이 있는데 접근성 서비스가 꺼져 있음(앱이 앞에 올 때 확인) | A |
| `prompt_fallback` | 액티비티가 0.8초 안에 안 떠서 오버레이로 대신함(백그라운드 실행 차단 의심) | A |
| `prompt_slow` | 감지 → 확인 화면 첫 그림이 기준(예: 1초 · placeholder)을 넘음 | A |
| `prompt_dismissed_unusual` | 사용자가 고르기 전에 짧은 시간 안에 닫힘이 반복 | A |
| `settings_route` | 설정 화면 직행 실패 · 사용한 길 | 온보딩 |
| `advanced_protection_on` | 고급 보호 모드 켜짐 | A |
| `alarm_late` | 확인 시각보다 N분 넘게 늦게 깸 | B(Phase 3) |
| `usage_access_lost` · `notification_denied` | 권한 꺼짐 | B |

## 3. 3층 구조 (추천)

```
① Play Console vitals ─── 크래시 · ANR (지금도 자동 · 비용 0 · 형제와 같은 방식)
② 기기 안 진단 기록 ───── 위 신호를 기기에 쌓는다(최근 N건 · 개수). 밖으로 안 나간다
③ 밖으로 보내기
   ③-a 자동 요약 ───── 하루 1회 "신호 종류별 개수 + 기기 정보"만 보낸다 → 서버 집계 → 기준 넘으면 디스코드 알림
   ③-b 문의 + 진단 첨부 ─ 문의 화면에 "진단 정보 함께 보내기"(기본 켬 · 보낼 내용 미리보기) → 문의와 같이 저장
```

- ③-a 가 **"사용자가 문의하지 않아도 우리가 바로 안다"** 를 맡는다. ③-b 가 **"문의할 때 로그를 같이"** 를 맡는다.
- 알림: 공용 서버에 이미 있는 **디스코드 웹훅**(문의 알림)을 같이 쓴다. 예: "SM-S921N · Android 16 에서 `service_lost` 가 오늘 20건".
- 보관: 자동 요약 90일(placeholder) · 문의 첨부는 문의와 같이 3년(공용 서버 문의 파기 기준).

### 3.1 왜 Sentry · Crashlytics 같은 SDK 가 아닌가 (추천하지 않는 이유)

- 이 앱의 실패는 크래시가 아니라 조용한 실패라 SDK 의 기본 기능이 거의 안 맞는다(§1).
- 제3자 SDK 가 기기 정보 · 식별자를 보내면 데이터 보안 양식 · 처리방침이 커지고 기둥 6 예외가 넓어진다.
- ~~형제 정책도 같다: 앱 크래시는 Play vitals, Sentry 는 서버용(`BUSINESS_INFO.md` §5.2).~~ → **정정(2026-10-08 · 사용자 지적 *"배구 게임은 쓰고 있어"*)**: 사업자 정본의 한 줄만 보고 형제 전체로 일반화했다. **배구명가는 앱 쪽 진단을 자체 구현해 쓰고 있다**(§3.2). Sentry 가 서버 전용이라는 것만 맞다.

### 3.2 형제 선례: 배구명가(`C:\project\volleyball` · `docs/BACKEND_SYSTEM.md` §8 · §13.20 · 텔레메트리 절)

| 데이터 보안 양식 | "수집 없음" → **"앱 정보 및 성능: 비정상 종료 로그 · 진단 정보 수집"**. 공유 없음 · 목적 = 앱 기능 · 분석 |
| 처리방침 | 수집 항목(기기 모델 · OS 버전 · 앱 버전 · 오류 신호) · 목적 · 보관 기간 · 거부 방법 |
| 공용 서버 | 🔴 **공용 서버는 일부러 OS 버전 · 기기 정보를 저장하지 않는다**(최소 수집 · `PLAN.md` §4). 진단 첨부 필드와 `diagnostics` 수집 경로는 **형제 전체가 쓰는 서버의 설계 변경**이다 → 공용 서버 세션에 요청하고 합의한다(`SESSION_PROTOCOL.md`). 이 저장소에서 공용 서버 코드를 직접 고치지 않는다 |
| 연령 확인 | 기기 토큰이 생기면 `GLOBAL_DATA_COMPLIANCE.md` §1 판정을 다시 한다(CLAUDE §4 의 ⚠ 가 이미 이 경우를 적어 둠) |
| 사용자 선택권 | 자동 요약을 끌 수 있는 설정(⚠ 기본값은 결정 필요) |

## 6. 결정 질문

1. 자동 요약(③-a)을 할까? 한다면 **기본 켬 + 설정에서 끄기** 인가, **처음에 물어보기**인가.
2. 문의 + 진단 첨부(③-b)의 기본값: 체크 켬인가 꺼짐인가.
3. 대상 앱 패키지 이름을 **문의 첨부에서만**, 사용자가 미리보기로 보고 보낼 때 넣을까(진단에 도움이 된다 · 개인정보는 커진다).
4. 공용 서버에 요청할까, 이 앱 전용 작은 수집 서버를 둘까(추천: 공용 서버 · 디스코드 · 기기 토큰이 이미 있다).
